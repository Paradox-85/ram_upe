For your situation, I would **not try to make OneLake the project's CDE**.

Instead, I would use **Fabric + OneLake as your organization's Information Management Layer** sitting above whichever client-mandated platform is being used.

That's actually very close to the ISO 19650 philosophy: separate the **information management process** from the **technology used for collaboration**. [\[learn.microsoft.com\]](https://learn.microsoft.com/en-us/fabric/onelake/onelake-overview), [\[windowsforum.com\]](https://windowsforum.com/threads/purview-on-fabric-and-onelake-unified-governance-for-safe-discoverable-ai.381065/)

## A minimal ISO 19650-aligned architecture

```text
Client A (ACC)
        │
Client B (ProjectWise)
        │
Client C (Dalux)
        │
        ▼
   Data Extraction
        │
        ▼
----------------------
 Microsoft Fabric
----------------------
        │
     OneLake
        │
 Metadata Model
        │
 Governance Rules
        │
 KPI / Monitoring
        │
 Information Register
```

The goal is not storing every file centrally.

The goal is creating a **single source of truth about information management**. OneLake is designed to act as a unified data layer with centralized governance across multiple sources. [\[learn.microsoft.com\]](https://learn.microsoft.com/en-us/fabric/onelake/onelake-overview), [\[learn.microsoft.com\]](https://learn.microsoft.com/en-us/fabric/onelake/quickstart-get-data)

## What I would standardize first

### 1. Common Information Register

Create a Lakehouse table containing:

```text
Project
Client
Platform
Container ID
Container Name
Discipline
Originator
Revision
Status
Suitability
Current State
Issue Date
Approval Date
```

Regardless of whether the source is ACC or ProjectWise, every document, model, drawing, report, and IFC becomes an information container in a common structure.

This gives you a corporate-level view of information flow.

***

### 2. Standard CDE States

Create a reference table:

```text
WIP
Shared
Published
Archived
```

Then map platform-specific statuses.

Example:

| ACC              | Corporate State |
| ---------------- | --------------- |
| Work in Progress | WIP             |
| Shared           | Shared          |
| Published        | Published       |

| ProjectWise | Corporate State |
| ----------- | --------------- |
| Draft       | WIP             |
| Review      | Shared          |
| Approved    | Published       |

This allows consistent reporting across projects.

***

### 3. Information Requirements Repository

Store:

```text
Project Information Requirements (PIR)
Asset Information Requirements (AIR)
Client Requirements
Deliverables
```

as structured records.

For example:

```text
Requirement:
Provide HVAC Asset Data

Purpose:
Facilities Management

Source:
AIR

Required Fields:
Asset ID
Manufacturer
Warranty
Maintenance Interval
```

Then link actual deliverables back to requirements.

This creates traceability that many BIM projects lack.

## Where Fabric becomes powerful

### Metadata over files

Many teams focus on file storage.

ISO 19650 is really about:

* information status
* information ownership
* approval
* suitability
* traceability

Fabric is excellent for this because OneLake can hold structured datasets from many sources while maintaining centralized governance. [\[learn.microsoft.com\]](https://learn.microsoft.com/en-us/fabric/onelake/onelake-overview), [\[learn.microsoft.com\]](https://learn.microsoft.com/en-us/fabric/onelake/security/get-started-security)

Think:

> "I don't need every Revit file in OneLake. I need all metadata about those Revit files."

***

## OneLake shortcuts are particularly interesting

OneLake supports connecting external storage through shortcuts without duplicating data. [\[learn.microsoft.com\]](https://learn.microsoft.com/en-us/fabric/onelake/quickstart-get-data), [\[learn.microsoft.com\]](https://learn.microsoft.com/en-us/fabric/onelake/onelake-overview)

In theory you could have:

```text
OneLake
 ├── Client A Data
 ├── Client B Data
 ├── Client C Data
```

where some data remains in external repositories but is discoverable through a unified governance layer.

For BIM organizations working with multiple owners, this is often preferable to copying terabytes of project information into a separate platform.

My recommendation: **position Fabric/OneLake as the corporate "Information Management Data Hub", not as a replacement CDE.** Let clients keep ACC, Dalux, Aconex, or ProjectWise. Fabric becomes the layer that standardizes metadata, requirements, workflows, reporting, and governance across all projects. That gives you a genuinely ISO 19650-aligned capability while avoiding fights about platform selection.
